## 2. 核心类型与接口清单

| 类型 / 函数 | 位置 | 职责 |
|------|------|------|
| `ProcessGroup` | `ProcessGroup.hpp` | 所有通信后端的抽象基类；虚方法返回 `c10::intrusive_ptr<Work>`；持有 rank/size 与 timeout |
| `Work` | `Work.hpp` | 异步通信句柄基类；`wait(timeout)` 阻塞等待，`getFuture()` 返回 `ivalue::Future` 供链式回调 |

| `GroupRegistry` | `GroupRegistry.hpp` | 维护全局默认组与命名组映射 |
| `ProcessGroup::Work` 选项 | `ProcessGroup.hpp` | 各集合原语的 `OpType`（SUM/PRODUCT/MAX...）与 `ReduceOp` 枚举 |

## 3. 关键调用链

1. **初始化进程组（`init_process_group`）**
   - Python 入口 `distributed_c10d.py:2370` 解析 `init_method`（env://、tcp://、file:// 或 store）。
   - 经 `rendezvous`（见 `../elastic`）建立或复用 `Store`，取得 world_size/rank。
   - 按 `backend` 实例化对应 `ProcessGroup` 子类（NCCL/Gloo/MPI/UCC），注册进 `GroupRegistry`，设为默认组。
2. **集合通信（如 `all_reduce`）**
   - Python `all_reduce`（`distributed_c10d.py:3962`）把张量与 `ReduceOp` 转交给默认 ProcessGroup。
   - `ProcessGroup::allreduce`（`ProcessGroup.hpp:256`）多态分派到具体后端，例如 `ProcessGroupNCCL` 在当前 CUDA 流上发起 `ncclAllReduce`，立即返回一个 `WorkNCCL`。
   - 用户对 `Work` 调 `wait()`/`synchronize()` 阻塞到该流上通信完成；或通过 `getFuture()` 注册回调异步完成。
3. **点对点（`send/recv`）**：`distributed_c10d.py:3502/3546` → `ProcessGroup::send/recv`（`ProcessGroup.hpp:815/839`）→ 后端把张量发到指定 peer rank。

## 5. 错误与重试语义

- **集合通信超时**：`Work::wait(timeout)` 超时抛分布式异常；`ProcessGroup::monitorredBarrier`（`ProcessGroup.hpp:787`）带超时的全局屏障用于检测挂起。
- **NCCL 异步错误**：`ProcessGroupNCCL` 有独立线程检测 NCCL 错误并通过 `Work` 的 `exception()`/`abort()` 上抛；`abort()`/`shutdown()`（`ProcessGroup.hpp:1023/1029`）用于异常退出。
- **Store 等待**：`Store::wait(keys, timeout)` 阻塞到键就绪或超时，是 rendezvous 的失败边界；本层不做自动重试，重试/重启由 `../elastic` 负责。
- **不保证重试**：单次集合通信调用失败即抛出，调用方（如 DDP）决定是否上抛；elastic 层负责进程级重启。

## 6. 并发细节

- **多进程模型**：c10d 本身不 fork 进程，每个 rank 一个进程，通过 NCCL/Gloo 库在进程间通信；进程编排由 `../elastic` 完成。
- **CUDA 流**：NCCL 后端在调用线程的当前 CUDA stream 上排队集合通信，`Work` 完成后 `blockCurrentStream()` 保证数据对后续流操作可见。
- **Work/Future 回调**：`Work::getFuture()` 返回 `c10::ivalue::Future`，通信完成时在后端线程触发回调，与 Python 侧异步通信钩子（`python_comm_hook.cpp`）配合。
- **Store 锁**：TCPStore server 端用互斥保护键值表；`PrefixStore` 对 key 加前缀做命名空间隔离。

## 7. 系统边界

**In-Scope（本仓库源码内）**
- `torch/distributed/distributed_c10d.py`：Python 前端 API 与进程组管理
- `torch/csrc/distributed/c10d/`：ProcessGroup/Work/Store 抽象及 NCCL/Gloo/MPI/UCC 后端实现、通信钩子

**Out-of-Scope（不在本仓库源码内）**
- NCCL、Gloo、MPI、UCC 通信库本体（vendored/外部依赖，仅做绑定）
- etcd 协调服务、TCP 主节点进程（外部组件）
- 高层数据并行策略（DDP/FSDP）见 `../ddp-fsdp`；RPC/DTensor 见 `../rpc-dtensor`；torchrun/弹性重启见 `../elastic`

## 8. 与相邻子系统交互

- **上层调用**：`torch/nn/parallel/distributed.py`（DDP）、`torch/distributed/fsdp/`（FSDP）、`torch/distributed/rpc/` 都通过 `distributed_c10d` 拿到默认/命名 ProcessGroup 发起集合通信。
- **下游依赖**：ProcessGroupNCCL → 外部 NCCL 库（CUDA 设备，见 `../../backends/cuda-backend/cuda-backend.md`）；ProcessGroupGloo → 外部 Gloo 库（CPU socket）。
- **协调**：rendezvous/Store 由 `../elastic` 与 `torch/distributed/rendezvous.py` 提供。

## 9. 语言专项适配口径

本项目为 **Python 前端 + C++ 核心**，不适用 Go（goroutine/informer/Reconciler）或 TypeScript（capability seam）专项。本节按 Python+C++ 口径分析：
- **C++ 侧**：`ProcessGroup` 是抽象基类，后端以多态继承实现（策略模式），`Work` 用 `c10::intrusive_ptr` 引用计数管理生命周期；并发靠 CUDA stream 与后端内部线程，而非 Go 式 goroutine。
- **Python 侧**：`distributed_c10d.py` 按"初始化 / 集合原语 / 点对点 / 组管理"能力缝组织，通过 pybind11 绑定到 C++ ProcessGroup。
- 依赖方向：Python API → C++ 抽象 → 具体后端 → 外部通信库，单向无环。
